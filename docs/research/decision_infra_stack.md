## 아젠다 ① 인프라: 서버리스 vs 자체 구축

### 후보

| | A. 서버리스 | B. 자체 구축 VM | C. 컨테이너 (ECS) |
|---|---|---|---|
| 구성 | Vercel + Supabase (Seoul) | EC2/Lightsail + RDS, Docker | Fargate + RDS + ALB |
| 월 비용(실질) | **0원** | 1.8만~11만원 | 9.4만원~ |

### 평가 축별 비교

| 축 | A. 서버리스 | B. 자체 VM | C. ECS |
|---|---|---|---|
| 보안성 | **우위** — OS·TLS·DDoS·패치를 플랫폼이 흡수, 공격면은 앱 코드뿐 | 공인 IP 상시 노출(자동 공격 대상), 패치·방화벽 구성 책임. 설정 실수 1건 = 침해 | VM보다 낫지만 IAM·NSG·SG 구성 복잡도가 곧 실수 면적 |
| 안정성 | 멀티테넌트 플랫폼 자동 복구. 단 cold start·7일 정지(완화 장치 가동 중) | **단일 VM = SPOF.** 장애 시 사람이 진단·복구 — *예: 오늘 겪은 Azure VM 무응답(원인: VM/NSG)처럼, 죽은 이유를 밖에서 알 수 없고 사람이 들어가야 한다* | 태스크 재스케줄링 자동 — 안정성 자체는 양호 |
| 확장성 | 자동 (입학 시즌 트래픽 무대응) | 수동 업사이즈 + 재시작 | 수평 확장 구성 가능 (이 규모에선 미사용 기능) |
| 모바일 친화성 | 서울 PoP CDN·엣지 캐시 — 첫 로딩 우위 | 단일 서버 직접 서빙 (CDN 별도 구성 필요) | ALB 뒤 직접 서빙 (CDN 별도) |
| 현대성 | 관리형·선언적 — 현 시점 표준 | 전통적 — 검증됐으나 운영 노동 동반 | 현대적이나 소규모엔 과한 추상화 |
| **AI 유지보수성** | **압도적 우위 (↓ 상세)** | 낮음 | 중간 |

### AI 유지보수성 상세 — 이 전제에서 가장 중요한 축

AI가 운영을 돕는 구조의 핵심은 **"시스템의 상태가 얼마나 repo 안의 코드로 표현되는가"**다.

| | A. 서버리스 | B/C. 자체 구축 |
|---|---|---|
| 관리 대상의 형태 | `vercel.json` + `supabase/migrations/*.sql` + GitHub Actions — **전부 repo 내 코드.** AI 세션이 컨텍스트로 전체 파악 가능 | Terraform으로 코드화해도 **서버 내부 상태(패치 수준·프로세스·디스크·로그)는 repo 밖** — AI가 SSH로 들어가 진단해야 하고, 코드와 실물의 드리프트가 누적 |
| 장애 대응 토큰 비용 | 운영 이벤트 자체가 드묾. 발생해도 플랫폼 대시보드 확인 수준 | 진단 세션(접속→로그 수집→가설 검증)이 회당 수만~수십만 토큰. *오늘 SSH 진단이 실례* |
| 정기 운영 토큰 비용 | ~0 (백업·ping 자동화 완료) | 패치·인증서·디스크·백업 검증이 주기적 AI/사람 세션 요구 |
| 재현성 | 계정만 있으면 `git clone` + 환경변수로 전체 재현 | 런북·IaC 문서화 품질에 의존 |

### 아젠다 ① 결론

- **서버리스(A) 권고 유지.** AI 개발 전제는 이 결론을 더 강화한다 — 자체 구축의 남은 정당화였던 "사람이 운영할 수 있다"는 역량 논거가 의미를 잃고, *운영 상태가 코드 밖에 존재한다*는 구조적 약점만 남는다
- **전환 트리거** (발동 시 B-적정화로 이전, standalone Docker 덕에 앱 재작성 불필요): ① 광고·모금 도입(Vercel 약관) ② Storage/egress 한도 정책으로 감당 불가 ③ 플랫폼 무료 정책 대폭 축소

## 아젠다 ② 기술 스택: FE / BE

### 후보

| | S-1. Next.js 풀스택 (현행) | S-2. React SPA + Express/Nest API | S-3. Next.js FE + 별도 BE |
|---|---|---|---|
| 코드베이스 | 1 (페이지+서버 로직 통합) | 2 (FE/BE 분리, REST 계약) | 2 (분리, FE도 서버 보유) |
| 권한 모델 | Supabase RLS 직결 | API 미들웨어 분기 (RLS 우회 관행) | 혼합 |

### 평가 축별 비교

| 축 | S-1. Next.js 풀스택 | S-2. SPA + Express API | S-3. Next FE + 별도 BE |
|---|---|---|---|
| 현대성 | React 공식 권장 방향(서버 컴포넌트), 활발한 발전 — 대신 변화 속도가 곧 업그레이드 비용 | Express는 안정적이나 2010년대 패턴. SPA+REST 조합 자체가 점차 레거시화 | BE(Nest 등)는 현대적이나 이 규모에 과설계 |
| 보안성 | **우위** — 세션 토큰이 서버(httpOnly 쿠키)에 머묾, 공격면 = 서버 액션 + RLS 이중 방어. 권한의 단일 진실 유지 | 토큰 브라우저 보관, API 엔드포인트 ~30개가 공격면, 권한을 앱 코드에 중복 구현(33개 게시판) → 드리프트 = 유출 | API 공격면 동일 + 복잡도 최대 |
| 안정성 | 계약 0개 — FE/BE 불일치라는 장애 유형 자체가 없음. DB→타입 자동생성으로 타입 정합 | **API 계약 정합이 최대 회귀 지점.** 배포 순서 의존, 버전 동기화 필요 | 계약 + 이중 서버 운영 |
| 확장성 | 추후 네이티브 앱 필요 시 Supabase(PostgREST)가 API 역할 — BE 분리 없이 대응 가능. route handler로 커스텀 API도 노출 가능 | "API 재사용" 이점은 Supabase 전제에서 이미 충족된 문제 | 동일 |
| 모바일 친화성 | **우위** — SSR 첫 로딩, 카톡 OG 미리보기(학부모 커뮤니티 핵심 유통 경로), 검색 노출, 이미지 최적화 내장 | SPA 구조적 결손: OG 미리보기 불가·SEO 상실·번들 로딩. SSR 추가 = Next.js 재발명 | FE가 Next라면 모바일 면은 S-1과 동일 |
| **AI 유지보수성** | **우위 (↓ 상세)** | 낮음 | 최저 |

### AI 유지보수성 상세 — 토큰 소요량 관점

기능 변경 1건(예: "게시판에 말머리 기능 추가")의 작업 표면:

| | S-1 풀스택 | S-2/S-3 분리형 |
|---|---|---|
| 수정 지점 | 마이그레이션 SQL + 페이지/액션 2~3파일 | 마이그레이션 + BE 라우트·검증·DTO + FE 훅·상태·타입 = **4~7곳, 2개 repo** |
| 세션 컨텍스트 | repo 1개 — 전체 구조가 한 컨텍스트에 들어옴 | repo 2개 + API 스펙 문서를 함께 로드 — **컨텍스트 ~2배, 변경당 토큰 ~1.5~2배** |
| AI 회귀 위험 | 타입은 DB에서 자동 생성(단방향) — 드리프트 구조적 차단 | **계약 드리프트가 AI 작업의 최빈 회귀 지점** (FE만 고치고 BE 누락 등) |
| 재생성 안전망 | 권한이 DB(RLS)에 — **앱을 통째로 재생성해도 권한 불변** | 권한이 앱 코드에 — 재생성마다 33개 게시판 권한 재검증 필요 |
| 학습 데이터 친화성 | Next.js·React·Express 모두 풍부 — 동률. 단 App Router 최신 패턴은 AI가 구버전 관행을 쓸 위험 → CLAUDE.md에 버전·패턴 명시로 완화(적용 중) | 동률 |

### 아젠다 ② 결론

- **S-1 (Next.js 풀스택 + Supabase) 권고.** 익숙함을 평가에서 제외하면 S-2의 유일한 강점이었던 조직 논거가 사라지고, 기술 축 전부와 AI 유지보수 축에서 S-1이 우위 또는 동률
- 핵심 논리: **AI가 코드를 쓰는 환경에서는 "코드가 적고, 계약이 없고, 불변식이 DB에 있는" 구조가 토큰 비용과 회귀 위험을 동시에 최소화한다**
- 프레임워크 종속 리스크 헤지: `output: "standalone"` + Docker (스택 결정 ≠ 인프라 결정), 고급 기능 미사용 유지, 연 1회 의존성 정리

## 두 아젠다의 결합 — 2×2

| | 스택: Next.js 풀스택 | 스택: SPA + Express |
|---|---|---|
| **인프라: 서버리스** | ✅ **현행 — 권고** (월 0원) | ❌ 사실상 불가 — Express 상시 서버가 서버리스 0원 전제와 충돌 |
| **인프라: 자체 구축** | ⭕ 가능 — standalone Docker로 무수정 이전 (트리거 발동 시 경로) | ⭕ 가능하나 아젠다②에서 탈락 |

주의: 두 아젠다는 독립적으로 결정할 수 있지만, **S-2(Express)를 고르면 인프라 선택지가 자체 구축으로 강제**된다(역방향 제약). S-1은 양쪽 인프라 모두 호환 — 의사결정 유연성까지 S-1의 이점이다.

## 최종 권고

1. **아젠다 ①: 서버리스 유지** — 비용 0원에 더해, AI 운영 전제에서 "상태가 전부 코드인" 유일한 선택지
2. **아젠다 ②: Next.js 풀스택 유지** — 모든 기술 축에서 우위/동률이며, 변경당 토큰 ~1/2, 재생성 안전망(RLS) 보유
3. 두 결정 모두 **되돌릴 수 있게 설계되어 있음** (표준 Postgres·pg_dump / standalone Docker) — 트리거가 구체화되는 시점에 재론하면 되고, 그때의 전환 비용도 낮다
