## 3. AWS 직접 구동에 필요한 기술 스택

"서버를 띄우는 것"과 "서비스를 운영하는 것"의 간극이 곧 운영 부담이다. 7인 그룹이면 역량 자체는 충족 가능 — 문제는 분담과 지속성이다.

### 3-1. 인프라 계층 (필수)

| 영역 | 필요 기술 | 비고 |
|---|---|---|
| 서버 기초 | Linux(systemd, 패키지 관리), SSH 키 관리, 보안그룹/방화벽 | 공인 IP는 24시간 자동 공격 대상 — fail2ban, 패치 주기 필수 |
| 웹 앞단 | Nginx(리버스 프록시, gzip, 정적 캐시), TLS 인증서(certbot 자동갱신 또는 ALB+ACM) | 갱신 실패 = 사이트 경고 |
| 런타임 | Docker + compose (권장) 또는 pm2 — 프로세스 재시작·로그 로테이션 | 멀티아치 빌드(t4g=ARM) |
| DB 운영 | PostgreSQL 설치·튜닝(RDS면 완화), **백업 자동화 + 외부 보관 + 복원 리허설**, 메이저 버전 업그레이드 | RDS 선택 시 상당 부분 위임 가능 |
| 배포 | CI/CD 파이프라인 — GitHub Actions → SSH/rsync 또는 ECR+CodeDeploy, 롤백 절차 | "장애 시 새벽에 손배포" 방지 장치 |
| 관측 | CloudWatch 에이전트(메모리·디스크), 외부 uptime 모니터, 알림 채널(Discord webhook) | 죽은 걸 회원 제보로 아는 상황 방지 |
| IaC·문서 | Terraform(권장) + 런북 — **인수인계의 핵심 장치** | 콘솔 수동 구축은 1년 뒤 아무도 재현 못 함 |

### 3-2. 애플리케이션 계층 (서버리스가 대신해주던 것들)

| Supabase가 하던 일 | 직접 구축 시 |
|---|---|
| Auth (가입·로그인·비밀번호 재설정 메일·세션) | NextAuth/Lucia + bcrypt + **SES 등 메일 발송 구축**(도메인 인증 SPF/DKIM 포함) — 개발 1~2주급 |
| Storage (권한 연동 파일) | S3 presigned URL + 권한 검사 미들웨어 직접 구현 |
| RLS (DB 레벨 권한) | 앱 코드 권한 분기로 회귀(현 설계 원칙 폐기) **또는 self-hosted Supabase**(docker 스택 — 그 자체가 운영 대상 추가) |
| 자동 백업·풀러·대시보드 | 직접 구축 목록에 추가 |

> 현 코드베이스는 Supabase SDK 의존(Auth/Storage/RLS)이므로, 완전 자체 구축 전환은 "서버 이전"이 아니라 **인증·파일·권한 계층 재개발 + 데이터 이전**이다. 다만 self-hosted Supabase를 쓰면 코드 변경 없이 이전 가능(운영 난도는 최상).

### 3-3. 운영 체계 (기술이 아닌 조직 요건)

- 운영 당번제(최소 2인 로테이션)와 장애 대응 채널 — "전원의 책임은 무책임"
- 보안 패치 SLA(예: critical 1주 내), 분기 1회 백업 복원 리허설
- 입사·이탈 시 권한 회수 절차(IAM·SSH 키)

## 4. 재분석: 개발자 7인은 무엇을 바꾸는가

### 바뀌는 것

- **"역량 부족" 논거 소멸**: 기존 문서의 핵심 반대 근거(전담 인력 없음 → 운영 불가)가 약해진다. 자체 구축은 "불가" → **"선택 가능"** 영역으로 이동
- 장애 대응·보안 패치·인수인계를 분담할 모수가 생긴다
- FE/BE 분리 같은 "팀 분업형 아키텍처"도 (비용 효율과 별개로) 운용은 가능해진다

### 바뀌지 않는 것

1. **비용**: 연 0원 vs 510만원(원안)/134만원(적정화)은 조합 예산 안건이다. 기술 역량과 무관
2. **자원봉사 운영의 구조적 리스크**: 7인은 "직원 7명"이 아니다 — 가용 시간 불규칙, 생업 우선, 자녀 졸업과 함께 이탈. 운영은 채용이 아니라 **당번제·문서화로 지속성을 설계**해야 하는 문제
3. **개발자 시간의 기회비용** — 이게 핵심이다. 7인의 시간은 조합의 가장 희소한 자원인데, 인프라 운영은 어느 회사에서나 "차별화 없는 무거운 일"이다. 같은 시간을 쓴다면:
   - 인프라 운영(서버리스가 0원에 해주는 일을 대체) ↔
   - **기능 개발**(검색·갤러리·예약 캘린더·에디터), **데이터 이관 품질**, **관리 도구** — 회원이 체감하는 가치
4. 트래픽 현실: 300명 규모에서 성능상 자체 구축이 필요해지는 시나리오는 없다 (기존 문서 §0·§3)

### 의사결정 프레임 — "할 수 있는가"가 아니라 "무엇에 시간을 쓸 것인가"

| 시나리오 | 적합 조건 | 연 비용(원) | 7인의 시간 사용처 |
|---|---|---|---|
| **권고: 단계적 하이브리드** — 지금은 서버리스로 오픈, 개발자 그룹은 기능·이관에 투입. 전환 트리거 발동 시 그룹이 이전 수행 | 현 상태 그대로 | 0 | 기능 개발 100% |
| 조건부 자체 구축 (D-2 적정화) | 아래 4개 조건 충족 시 | ~134만 | 운영 ~20% + 기능 80% |
| 제안 원안 (D-1, 4서버+2DB) | 사이트 다수 확장 계획 + 예산 여유 | ~510만 | 운영 ~30% |

**조건부 자체 구축의 4가지 선행 조건** (하나라도 빠지면 1~2년 내 방치 위험):
1. 조합 총회의 **연 예산 승인** (134만~510만원, 매년)
2. **운영 당번제 합의** — 최소 2인 로테이션, 방학 포함
3. **IaC(Terraform) + 런북 문서화**를 구축 완료 조건에 포함
4. 분기 1회 **백업 복원 리허설** 일정화

### 결론

- 개발자 그룹의 존재는 자체 구축을 "가능"하게 만들지만 "유리"하게 만들지는 않는다. **이 규모에서 자체 구축이 이기는 항목은 '약관 자유(광고·모금)'와 '상시 구동' 단 둘**이고, 둘 다 현재 미발동 상태다(모금 도입 시 재론).
- 제안 견적(D-1)은 컴퓨팅 단가는 정확하나 **이 워크로드의 4배 사양**이다. 자체 구축으로 가더라도 D-2(월 11만원)에서 시작해 필요 시 키우는 것이 합리적.
- **가장 비싼 자원은 AWS가 아니라 개발자 7인의 시간**이다. 그 시간을 인프라(이미 0원에 해결된 문제)보다 기능·이관·관리도구(아직 해결 안 된 문제)에 쓰는 것이 조합 관점의 ROI가 높다 — 이것이 서버리스 "원칙"이 아닌, 현 시점 자원 배분의 결론이다.

## 5. 스택 전환 검토: Express + React(SPA) vs 현행 Next.js 풀스택 (2026-06-12 추가)

> 검토 배경: "사람들이 익숙한 스택이 유지보수에 유리하다"는 개발자 그룹 의견. Node-Express BE + React SPA FE로의 전환안을 비교한다.

### 5-1. 전환안이 옳게 짚은 것

- **Express는 지루하고 안정적이다**: 10년간 API가 거의 안 변했고, 아는 사람이 많다. 반면 Next.js는 메이저 버전마다 패러다임이 이동해 온 이력(Pages→App Router)이 있어 "방치된 Next.js 앱"의 업그레이드 비용은 실재하는 리스크다
- **유지보수 주체가 아는 스택이어야 한다**는 명제 자체는 조직 현실로서 타당하다 — 스택은 기술 우열이 아니라 "누가 고칠 것인가"로 결정되는 것이 맞다

### 5-2. 그러나 "익숙함"의 전제를 다시 보면

**현행 스택에서 개발자가 다루는 코드는 이미 대부분 React다.** Next.js는 React 프레임워크이고, 현 프로토타입의 컴포넌트·훅은 전부 표준 React 문법이다. 낯선 부분은 데이터 패칭 패턴 하나로 좁혀진다:

| 작업 | Express+React에서 | 현행 Next.js에서 |
|---|---|---|
| 목록 조회 | Express 라우트 작성 → fetch + useEffect/React Query + 로딩 상태 관리 | 서버 컴포넌트에서 `await supabase.from(...)` 한 줄 |
| 글 등록 | POST 라우트 + 검증 + 클라이언트 fetch + 에러 처리 | 서버 액션 함수 하나 |
| 인증 확인 | 미들웨어 + 토큰 검증 + 클라이언트 상태 동기화 | `getUser()` (RLS가 이중 방어) |

Express를 아는 개발자에게 서버 액션은 "라우트 핸들러가 함수 호출로 바뀐 것"에 가깝다 — 학습 격차는 며칠 단위이지, 스택 재선정을 정당화하는 수준이 아니다.

### 5-3. 전환 시 실제로 늘어나는 것 — 유지보수 표면적

유지보수성의 일차 결정 요인은 익숙함보다 **고쳐야 할 코드의 양과 계약의 수**다.

| 항목 | 현행 (Next.js 풀스택) | Express + React SPA |
|---|---|---|
| 코드베이스 | 1개 (페이지+로직 동일 저장소·언어·배포) | **2개** (FE/BE 별도 빌드·배포·버전 정합) |
| API 계층 | **없음** (서버 액션 + RLS 직결) | REST 엔드포인트 ~30개 설계·검증·문서화·CORS |
| 클라이언트 상태 | 최소 (서버 렌더 중심) | React Query/SWR + 로딩·에러·캐시 관리 전면 도입 |
| 권한 강제 | RLS 단일 진실 (현 설계 원칙) | Express 미들웨어 권한 분기 — **33개 게시판 권한을 앱 코드에 중복 구현**하는 회귀 위험 |
| 추정 유지보수 표면적 | 기준 1.0 | **약 1.5~2.0배** |

### 5-4. SPA가 만드는 기능 결손 — 이 프로젝트에 특히 치명적인 것

1. **카카오톡 링크 미리보기(OG 태그)**: 학부모 커뮤니티의 공지 유통 경로는 사실상 카톡이다. SPA는 모든 URL이 같은 빈 HTML을 반환하므로 **글 제목·요약이 미리보기에 안 뜬다.** 해결하려면 Express에 SSR을 붙여야 하는데, 그 순간 Next.js를 손으로 재발명하는 것이 된다
2. **검색엔진 노출**: 공개 게시판(공지·입학 안내)의 검색 유입 상실
3. **모바일 첫 로딩**: 마이그레이션 핵심 목적(모바일 UX)과 역행 — SPA는 JS 번들 전체를 받아야 첫 화면이 뜬다
4. 이미지 최적화·코드 스플리팅·라우팅을 라이브러리 조합으로 직접 구성 (Vite+router+상태관리 — 이 조합 역시 변화가 빠른 생태계다)

### 5-5. 비용 결합 효과

| | 현행 | Express+React |
|---|---|---|
| 재개발 | 0 (1차 프로토타입 완성·배포됨) | **프로토타입 폐기 + API 서버 신규 개발** (1차 구축분 재투입 이상) |
| 호스팅 | Vercel Hobby $0 | Express 상시 서버 필요 → **0원 옵션 소멸**, 최소 Lightsail $13~/월부터 (§2 표) |
| Supabase 관계 | Auth/Storage/RLS 그대로 | DB·Auth는 유지 가능하나, Express 관행(service key 중앙 접근)을 따르면 RLS 무력화 — 의식적으로 지켜야 함 |

### 5-6. 절충안 — 전환 없이 우려를 해소하는 방법

전환안이 해결하려는 진짜 문제는 "Next.js 종속 리스크"다. 이는 스택 교체 없이 헤지 가능하다:

1. **Next.js standalone 출력 + Docker**: `output: "standalone"` 설정이면 현행 코드가 그대로 **Express처럼 단일 Node 서버로 자체 호스팅**된다 — 인프라를 자체 구축으로 전환하더라도 스택 재작성이 필요 없다 (스택 결정 ≠ 인프라 결정)
2. **이미 단순하게 쓰고 있다**: 현 코드는 Next.js 고급 기능(병렬 라우트, 인터셉트 등) 없이 "페이지 + 서버 액션"만 사용 — 업그레이드 충격면이 작다
3. 메이저 업그레이드는 연 1회 의존성 정리 당번(개발자 그룹)으로 흡수 — Express를 택해도 React/빌드체인 업그레이드는 어차피 발생한다

### 5-7. 결론 (1차 — 재작성 비용을 포함한 분석)

- **전환 비권고.** "익숙함"이 실제로 절약해주는 학습 비용(며칠)보다, 잃는 것(작동하는 프로토타입 폐기, 유지보수 표면적 1.5~2배, 카톡 미리보기·SEO·모바일 첫 로딩, 0원 호스팅, RLS 단일 진실)이 구조적으로 크다
- 유지보수성 우려의 본질(프레임워크 종속)은 **standalone Docker 헤지 + 단순한 사용 범위 유지**로 대응하는 것이 합리적
- 단, 의사결정 원칙은 유지: **실제로 유지보수를 맡을 사람이 끝내 Next.js를 거부한다면 그 조직 현실이 우선한다.** 그 경우에도 순서는 "지금 전환"이 아니라 — 현행으로 오픈 → 운영하며 그룹이 서버 액션 패턴을 직접 평가 → 그래도 거부 시 2차 개편에서 전환 — 이어야 작동 중인 결과물을 잃지 않는다

### 5-8. 재분석: "재작성 비용 ≈ 0" 전제 (AI 개발 — 2026-06-12 추가)

> 반론 수용: 프로토타입은 Claude Code로 언제든 재작성 가능하므로 개발 비용은 의사결정에서 제외한다. 이 전제에서 분석을 다시 세운다.

**무너지는 논거 (철회)**

- "작동하는 프로토타입 폐기" — 재작성이 공짜라면 매몰비용 논거는 성립하지 않는다 (5-5 재개발 행, 5-7 첫 항목 일부 철회)
- "API 서버 신규 개발량 ~2배" — 작성 비용 관점에서는 무의미해진다. AI는 코드 30,000줄도 3,000줄도 써준다

**남는 논거 — 개발 비용이 0이어도 변하지 않는 것**

개발 비용을 제거하면 선택 기준은 순수하게 **런타임·운영 특성**으로 좁혀지는데, 이 기준에서는 결과가 달라지지 않는다:

| 특성 | 누가 코드를 쓰든 동일한가 | 판정 |
|---|---|---|
| 카톡 OG 미리보기·SEO·모바일 첫 로딩 | SPA의 구조적 속성 — AI가 잘 짜도 동일 | 현행 우위 |
| 호스팅 비용 (Express = 상시 서버 = 0원 소멸) | 아키텍처 속성 | 현행 우위 |
| 운영 표면적 (배포 2개, API 계약 정합, CORS, 버전 동기화) | **작성은 공짜여도 운영·장애 지점은 2배로 실재** | 현행 우위 |
| 권한 아키텍처 (RLS vs 앱 분기) | 설계 속성 | 현행 우위 (아래 ↓) |

**새로 생기는 논점 — 오히려 AI 전제가 현행 설계를 강화한다**

1. **코드가 싸질수록 DB 불변식(RLS)의 가치는 올라간다.** "언제든 재작성"이 가능한 세계에서는 앱 코드가 자주, 크게 바뀐다. 권한이 앱 코드에 있으면(Express 방식) **재작성할 때마다 33개 게시판 권한 로직을 재검증**해야 하고, 한 번의 재생성 실수가 곧 정보 유출이다. 권한이 DB에 있으면(현행) 앱을 통째로 갈아엎어도 권한은 유지된다 — **재작성 자유의 안전망이 바로 RLS다**
2. **AI 유지보수 효율도 단일 코드베이스가 유리하다.** FE/BE 분리는 AI에게도 "두 저장소 + 그 사이 API 계약"이라는 동기화 지점을 만든다. 계약 불일치는 AI 작업에서도 가장 흔한 회귀 지점이다
3. **재작성 자유는 양방향이고, 시간이 갈수록 감쇠한다.** 지금 Express로 바꾸는 비용이 0이라면, *나중에* 바꾸는 비용도 0이다 — 즉 서두를 이유가 사라진다(기다림의 옵션 가치). 반대로 오픈 후에는 데이터·URL·운영 자동화·사용자 습관이 쌓여 "공짜 재작성" 전제 자체가 약해진다. **코드는 싸지만, 가동 중인 시스템은 싸지 않다**

**결론 (갱신)**

- 재작성 무비용 전제를 받아들여도 **전환 비권고는 유지된다** — 다만 근거가 바뀐다: "다시 만들기 아까워서"가 아니라, **개발 비용을 0으로 놓고 런타임·운영 특성만 비교했을 때 Express+React(SPA)가 이기는 항목이 하나도 없기 때문**이다
- 전환이 정당해지는 유일한 조건은 구조적 필요가 생길 때(예: 별도 네이티브 앱용 API — 이것도 Supabase가 PostgREST로 이미 제공)다. 그 필요가 구체화되면 **그때 바꿔도 비용이 같다** — 이것이 AI 전제의 진짜 함의다
- 부수 효과: 같은 논리로 "조합 개발자 그룹의 익숙함" 가중치도 낮아진다. 코드를 주로 쓰는 주체가 AI라면, 스택 선택 기준은 사람의 익숙함보다 **AI가 다루기 쉬운 구조(단일 코드베이스·적은 계약·DB 불변식)**가 된다 — 이 기준 역시 현행을 가리킨다
