### 1-4. 아키텍처 적정성 — 이 견적의 진짜 문제는 단가가 아니라 구조

회원 300명·동접 수십 명 기준으로 두 가지 과투자가 겹쳐 있다.

1. **FE/BE 분리 전제**: Next.js는 풀스택 프레임워크다(현 프로토타입도 서버 액션으로 BE 역할 수행 중). BE를 별도 서버로 분리하면 **API 서버를 새로 개발**해야 하고(개발량 ~2배), 그걸 위해 서버 2대가 추가된다. 이 규모에서 분리가 주는 이점(독립 스케일링, 팀 분업)은 발생하지 않는다.
2. **dev를 prd와 동일 사양으로 상시 구동**: dev는 트래픽이 0에 수렴한다. 동일 사양 상시 구동은 비용 ×2를 만드는 가장 흔한 패턴.

## 3. AWS 직접 구동에 필요한 기술 스택

"서버를 띄우는 것"과 "서비스를 운영하는 것"의 간극이 곧 운영 부담이다. 7인 그룹이면 역량 자체는 충족 가능 — 문제는 분담과 지속성이다.

### 3-1. 인프라 계층 (필수)

| 영역 | 필요 기술 | 비고 |
|---|---|---|
| 서버 기초 | Linux(systemd, 패키지 관리), SSH 키 관리, 보안그룹/방화벽 | 공인 IP는 24시간 자동 공격 대상 — fail2ban, 패치 주기 필수 |
| 웹 앞단 | Nginx(리버스 프록시, gzip, 정적 캐시), TLS 인증서(certbot 자동갱신 또는 ALB+ACM) | 갱신 실패 = 사이트 경고 |
| 런타임 | Docker + compose (권장) 또는 pm2 — 프로세스 재시작·로그 로테이션 | 멀티아치 빌드(t4g=ARM) |
| DB 운영 | PostgreSQL 설치·튜닝(RDS면 완화), **백업 자동화 + 외부 보관 + 복원 리허설**, 메이저 버전 업그레이드 | RDS 선택 시 상당 부분 위임 가능 |
| 배포 | CI/CD 파이프라인 — GitHub Actions → SSH/rsync 또는 ECR+CodeDeploy, 롤백 절차 | "장애 시 새벽에 손배포" 방지 장치 |
| 관측 | CloudWatch 에이전트(메모리·디스크), 외부 uptime 모니터, 알림 채널(Discord webhook) | 죽은 걸 회원 제보로 아는 상황 방지 |
| IaC·문서 | Terraform(권장) + 런북 — **인수인계의 핵심 장치** | 콘솔 수동 구축은 1년 뒤 아무도 재현 못 함 |

### 3-2. 애플리케이션 계층 (서버리스가 대신해주던 것들)

| Supabase가 하던 일 | 직접 구축 시 |
|---|---|
| Auth (가입·로그인·비밀번호 재설정 메일·세션) | NextAuth/Lucia + bcrypt + **SES 등 메일 발송 구축**(도메인 인증 SPF/DKIM 포함) — 개발 1~2주급 |
| Storage (권한 연동 파일) | S3 presigned URL + 권한 검사 미들웨어 직접 구현 |
| RLS (DB 레벨 권한) | 앱 코드 권한 분기로 회귀(현 설계 원칙 폐기) **또는 self-hosted Supabase**(docker 스택 — 그 자체가 운영 대상 추가) |
| 자동 백업·풀러·대시보드 | 직접 구축 목록에 추가 |

> 현 코드베이스는 Supabase SDK 의존(Auth/Storage/RLS)이므로, 완전 자체 구축 전환은 "서버 이전"이 아니라 **인증·파일·권한 계층 재개발 + 데이터 이전**이다. 다만 self-hosted Supabase를 쓰면 코드 변경 없이 이전 가능(운영 난도는 최상).

### 3-3. 운영 체계 (기술이 아닌 조직 요건)

- 운영 당번제(최소 2인 로테이션)와 장애 대응 채널 — "전원의 책임은 무책임"
- 보안 패치 SLA(예: critical 1주 내), 분기 1회 백업 복원 리허설
- 입사·이탈 시 권한 회수 절차(IAM·SSH 키)

## 4. 재분석: 개발자 7인은 무엇을 바꾸는가

### 바뀌는 것

- **"역량 부족" 논거 소멸**: 기존 문서의 핵심 반대 근거(전담 인력 없음 → 운영 불가)가 약해진다. 자체 구축은 "불가" → **"선택 가능"** 영역으로 이동
- 장애 대응·보안 패치·인수인계를 분담할 모수가 생긴다
- FE/BE 분리 같은 "팀 분업형 아키텍처"도 (비용 효율과 별개로) 운용은 가능해진다

### 바뀌지 않는 것

1. **비용**: 연 0원 vs 510만원(원안)/134만원(적정화)은 조합 예산 안건이다. 기술 역량과 무관
2. **자원봉사 운영의 구조적 리스크**: 7인은 "직원 7명"이 아니다 — 가용 시간 불규칙, 생업 우선, 자녀 졸업과 함께 이탈. 운영은 채용이 아니라 **당번제·문서화로 지속성을 설계**해야 하는 문제
3. **개발자 시간의 기회비용** — 이게 핵심이다. 7인의 시간은 조합의 가장 희소한 자원인데, 인프라 운영은 어느 회사에서나 "차별화 없는 무거운 일"이다. 같은 시간을 쓴다면:
   - 인프라 운영(서버리스가 0원에 해주는 일을 대체) ↔
   - **기능 개발**(검색·갤러리·예약 캘린더·에디터), **데이터 이관 품질**, **관리 도구** — 회원이 체감하는 가치
4. 트래픽 현실: 300명 규모에서 성능상 자체 구축이 필요해지는 시나리오는 없다 (기존 문서 §0·§3)

### 의사결정 프레임 — "할 수 있는가"가 아니라 "무엇에 시간을 쓸 것인가"

| 시나리오 | 적합 조건 | 연 비용(원) | 7인의 시간 사용처 |
|---|---|---|---|
| **권고: 단계적 하이브리드** — 지금은 서버리스로 오픈, 개발자 그룹은 기능·이관에 투입. 전환 트리거 발동 시 그룹이 이전 수행 | 현 상태 그대로 | 0 | 기능 개발 100% |
| 조건부 자체 구축 (D-2 적정화) | 아래 4개 조건 충족 시 | ~134만 | 운영 ~20% + 기능 80% |
| 제안 원안 (D-1, 4서버+2DB) | 사이트 다수 확장 계획 + 예산 여유 | ~510만 | 운영 ~30% |

**조건부 자체 구축의 4가지 선행 조건** (하나라도 빠지면 1~2년 내 방치 위험):
1. 조합 총회의 **연 예산 승인** (134만~510만원, 매년)
2. **운영 당번제 합의** — 최소 2인 로테이션, 방학 포함
3. **IaC(Terraform) + 런북 문서화**를 구축 완료 조건에 포함
4. 분기 1회 **백업 복원 리허설** 일정화

### 결론

- 개발자 그룹의 존재는 자체 구축을 "가능"하게 만들지만 "유리"하게 만들지는 않는다. **이 규모에서 자체 구축이 이기는 항목은 '약관 자유(광고·모금)'와 '상시 구동' 단 둘**이고, 둘 다 현재 미발동 상태다(모금 도입 시 재론).
- 제안 견적(D-1)은 컴퓨팅 단가는 정확하나 **이 워크로드의 4배 사양**이다. 자체 구축으로 가더라도 D-2(월 11만원)에서 시작해 필요 시 키우는 것이 합리적.
- **가장 비싼 자원은 AWS가 아니라 개발자 7인의 시간**이다. 그 시간을 인프라(이미 0원에 해결된 문제)보다 기능·이관·관리도구(아직 해결 안 된 문제)에 쓰는 것이 조합 관점의 ROI가 높다 — 이것이 서버리스 "원칙"이 아닌, 현 시점 자원 배분의 결론이다.
